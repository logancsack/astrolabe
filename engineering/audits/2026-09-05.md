## Changes and evidence

| Finding | Change | Verification |
| --- | --- | --- |
| Both SSE endpoints left the upstream open after a client disconnected, and hung the client after upstream failure. | Use Node's stream pipeline to couple stream lifetime and propagate failure. Destroy a stream arriving after its client is already gone. | Six real HTTP streaming tests: incremental delivery passed before; disconnect/error cases failed or timed out before and all pass after. |
| Permanent upstream authentication errors triggered another request on a wider model tier. | Respect `isRetryableModelError` before crossing tiers. | Both APIs made two requests before the fix and one afterward for a 401. |
| Chat and Responses duplicated metadata/header handling, rescanned messages, and rebuilt candidates. Stream requests built JSON metadata they discarded. | Share completion handling, retain the original candidates, and skip unused stream metadata. | Existing API, fallback, schema, and policy tests pass. |
| Heuristics compiled the same static regular expressions for each call; structured-output detection rescanned the same conversation in several routing stages. | Compile category patterns once and retain the structured-output decision only within the normalized request. | Benchmarks below; regression confirms old conversation context still triggers structured output and a subsequent request does not inherit the decision. |
| Tests reloaded the production entry point, mutated process environment and module caches, and duplicated HTTP request code. | Construct isolated configs/apps/runtimes directly; make JSON requests reuse the raw HTTP helper. | Baseline: 58/58 pass normally, but 32 fail with unrelated API-key/force-model shell settings. Final: all 67 pass both normally and with those settings, without credentials. |
| Unused imports, obsolete policy regex constants, unreachable text checks, and a conditional returning the same value on both branches obscured the runtime. | Remove only those dead paths. Keep meaningful routing, policy, and roster assertions. | Full existing suite retained. |
| Locked dependencies had five npm audit findings, including two high-severity entries. | Refresh compatible lockfile versions, including Axios and its transport dependencies. | Fresh `npm ci`, real HTTP transport tests, and `npm audit`: zero findings. |
| No reusable benchmark/public smoke loop; catalog fetch could wait indefinitely. | Add focused npm scripts, benchmark, unauthenticated Cloud smoke command, worktree/debug guidance, and 15-second catalog timeout. | Smoke command exits 0 for a healthy local contract fixture and 1 for a bad health marker; live production detects the missing documented route. |

The streaming change follows [Node's stream pipeline lifecycle](https://nodejs.org/api/stream.html#streampipelinesource-transforms-destination-callback). It does not implement cancellation while waiting for upstream response headers, and it does not add post-verification of SSE tool calls. Neither model selection defaults nor approval policy was changed.

## CPU measurements

`node scripts/benchmark-runtime.js`: seven samples after warmup. Axios is stubbed; no network or model execution. The long-context workload contains 256 alternating text messages, about 266 KB of content. The same 15,000 upstream stub calls were made before and after.

| Workload | Before median | After median | Reduction |
| --- | ---: | ---: | ---: |
| Heuristic coding classification | 4.73 µs | 2.63 µs | 44.4% |
| Long-context Chat request setup | 4,631.49 µs | 3,867.20 µs | 16.5% |
| Long-context stream setup | 4,540.95 µs | 3,793.32 µs | 16.5% |

Before min/max: heuristic 4.65–5.99 µs; Chat 4,605.56–4,763.19 µs; stream setup 4,503.27–4,762.98 µs. After: 2.52–3.80 µs, 3,769.88–3,897.36 µs, and 3,765.40–3,880.67 µs respectively.

An intermediate cleanup-only run did **not** improve long-context timing (4,663.27 µs Chat; 4,638.60 µs stream setup). Avoiding repeated structured-output scans produced that improvement. These are gateway CPU results, not production latency or throughput claims.

## Remaining OSS audit findings

1. **Configuration controls with no runtime effect.** `ALLOW_DIRECT_PREMIUM_MODELS` and `ALLOW_HIGH_STAKES_BUDGET_FLOOR` are parsed but never consumed. `COST_EFFICIENCY_MODE` is reported in health but does not drive routing. The `low-latency` default profile is accepted without profile-specific behavior. These public options need an explicit implementation/deprecation decision; removing them casually could break downstream expectations.
2. **Routing documentation conflict.** AGENTS.md says to treat `m27` as the serious-work default, while the current manifest, tests, and README intentionally start auto/coding with DeepSeek V4 Pro. This audit preserved the checked-in behavior. Reconcile the instruction with the intended policy separately.
3. **Deployment boundaries.** README describes OSS; the Mintlify docs now describe Cloud stacks, billing, state, and trace storage. Agents need a clear repository/deployment map to avoid applying OSS assumptions to Cloud. The verification guide records this distinction.
4. **Long-running upstream requests.** Stream requests have no upstream timeout before headers, and client cancellation during classifier/verifier/nonstream work is not propagated to Axios. Adding a request-scoped abort signal and bounded time-to-headers is the next resource-control improvement; it needs tests across fallback and verification to ensure cancellation never starts another model call.
